# Исследование REST API и принятые решения

> Подтверждённые имена полей, стадии, синтаксис фильтров, открытые вопросы для портала `<portal>.bitrix24.ru`.

Updated: 2026-10-08

## Сводка

**Topic:** Локальное приложение Битрикс24 «Дебиторка» (ранее «Отчёт по счетам») для портала `<portal>.bitrix24.ru` (адаптация существующего приложения под новый портал).

**Goal:** Сводный отчёт по контактам и по ответственным сотрудникам (две вкладки, одни и те же счета) с агрегацией сумм по умным счетам (Smart Invoice 2.0, `entityTypeId=31`) и KPI «% сбора дебиторки» = Оплачено / Должен всего. Закрывает дыру BI-конструктора (там нельзя задать два независимых диапазона дат).

**Колонки таблицы (на контакт):**
1. ФИО контакта (кликабельно — открывает карточку контакта в слайдере)
2. Должен всего  = `SUM(opportunity)`
3. Оплачено      = `SUM(opportunity WHERE stageId == 'DT31_5:P')`
4. Просрочено    = `SUM(opportunity WHERE stageId != 'DT31_5:P' AND closedate < today)`
5. Остаток к оплате = `SUM(opportunity WHERE stageId != 'DT31_5:P')`

**Фильтры:**
- Ответственный за **счёт** (`assignedById` в `crm.item.list`, фильтр на клиенте, `@assignedById` не отправляется) — multi-select. Список — ответственные счетов за период, ФИО через `user.get` с `FILTER: {ID: [...]}`, включая уволенных («(уволен)»). Причина (2026-10-08): на портале 20 из 23 владельцев счетов уволены, а список активных (`ACTIVE: 'Y'`) давал 12 пользователей, в основном без счетов.
- Срок оплаты от/до (`closedate`).
- Дата оплаты от/до (`ufCrmSmartInvoiceDatePay`, постфильтр на клиенте).
- По умолчанию: `closedate` = первое..последнее число текущего месяца.

Фильтр по договорам из исходного приложения удалён целиком (решение пользователя 2026-10-08): сделки не загружаются, поля договора не используются.

**Constraints:**
- Тип приложения: статичное локальное (ZIP через «Приложения → Разработчикам → Другое → Локальное приложение»), без бэкенда.
- Объём: ~1 800 счетов всего в портале (1 739 после удаления счетов без контакта и со странными сроками), за типичный месяц ~5–15, данные в основном 2021–2025. По объёму ограничений нет.
- Воронка одна: `categoryId=5` «Общее».
- REST-методы: `crm.item.list`, `crm.contact.list`, `user.get`, классический `batch`.

## Подтверждённые поля (`crm.item.list`, entityTypeId=31, camelCase)

- `id`, `contactId`, `assignedById`, `opportunity` (Сумма, double)
- `stageId` — см. таблицу стадий
- `closedate` — Срок оплаты (date, ISO с `+03:00`)
- `ufCrmSmartInvoiceDatePay` — Дата фактической оплаты (date; поле на портале есть)
- `categoryId=5` — единственная воронка

Контакты (`crm.contact.list`) — UPPER_SNAKE: `ID`, `NAME`, `LAST_NAME`, `SECOND_NAME`.

## Стадии (`categoryId=5` «Общее»)

| `stageId` | Название | Semantics | В отчёте |
|---|---|---|---|
| `DT31_5:N` | Новый | — | в работе |
| `DT31_5:S` | Отправлен клиенту | — | в работе |
| `DT31_5:UC_2SOUNY` | Три дня до | — | в работе |
| `DT31_5:UC_9SXLKB` | Оплата сегодня | — | в работе |
| `DT31_5:UC_0DRSDP` | Просрочен на 3 | — | в работе |
| `DT31_5:UC_VQM7R0` | Совсем просрочен (21 день) | — | в работе |
| `DT31_5:UC_YUR7QW` | Замороженные платежи | — | в работе; просрочка — только по дате |
| `DT31_5:P` | Оплачен | S | `is_paid = true` |
| `DT31_5:D` | Не оплачен | F | отсекается серверным фильтром |

**Правило:** `is_paid := (stageId == 'DT31_5:P')`. Любая другая стадия, кроме отсечённой `DT31_5:D`, — в работе → «Остаток», а при `closedate < today` ещё и «Просрочено».

Отличие от исходного портала: там `:D` была черновиком, здесь `DT31_5:D` — финальная неуспешная стадия «Не оплачен». Поведение (исключение из отчёта) сохранено, нужно подтверждение (см. ниже).

## Синтаксис фильтров и batch

- Операторы фильтра в `crm.item.list` (`>=closedate`, `<=closedate`, `!=stageId`, `@assignedById`; последний приложение с 2026-10-08 не использует) при прямом обращении к webhook работают **только** как POST с `Content-Type: application/json`:
  ```json
  {
    "entityTypeId": 31,
    "filter": {
      ">=closedate": "2024-01-01",
      "<=closedate": "2024-12-31",
      "!=stageId": "DT31_5:D",
      "@assignedById": [1, 19]
    },
    "select": ["id","contactId","assignedById","opportunity","stageId","closedate","ufCrmSmartInvoiceDatePay"],
    "start": 0
  }
  ```
  GET `?filter[>=closedate]=…` и POST form-urlencoded фильтр молча игнорируют. Через `BX24.callMethod` на портале сериализация корректна.
- Имена полей — строго как в `crm.item.fields`: `>=closedate`, не `>=closeDate`.
- Внутри классического `batch` (dev: один POST на `{webhook}batch`, команды сериализует `toBitrixQuery`) операторы фильтра работают.
- Batch v3 (`/rest/api/.../batch`) CRM-методы не поддерживает (проверено 2026-10-05 на прежнем портале) — используется классический `batch` (≤ 50 команд).

## Решения пользователя (2026-10-08)

- **«Замороженные платежи»** (`DT31_5:UC_YUR7QW`) — обычная стадия «в работе»: просрочка только по дате (`closedate < today`), отдельной логики нет.
- **`opportunity = 0` — норма.** При переплате счёт не удаляют, а переносят его сумму в счёт, который оплачивается; обнулённый счёт остаётся. Нулевые счета на суммы не влияют — так и должно быть.
- **Счета без контакта удалены на портале** (110 шт.: 73 «Совсем просрочен», 30 «Замороженные платежи», 7 «Оплачен»; у 36 была сделка, компании — ни у одного). Удалены через `crm.item.delete` по одному (в dev-batch с JSON-телом `crm.item.delete` молча не сработал). Копия удалённых счетов удалена по решению пользователя. После удаления на портале 1 790 счетов. Код по-прежнему отбрасывает счета без `contactId` — на случай новых.
- **Колонка «% сбора» в строках не нужна** — только общий KPI у фильтра.
- **Формула «% сбора» остаётся** = Оплачено / Должен всего по счетам с `closedate` в периоде (`aggregator.collectionRate`).
- **Активная вкладка в URL не хранится** — не нужно.
- **`DT31_5:D` «Не оплачен» не учитываем** — отсекается серверным фильтром (`!=stageId`).
- **Оплаченный счёт без даты оплаты:** датой оплаты считается срок оплаты (`closedate`) — для фильтра «Дата оплаты от/до» (`isDatePayInRange` в `data-loader.js`). В CRM поле не заполняется. На портале таких 19, все 2022 года; проверка фильтра «Дата оплаты 2022»: было 0 счетов, стало 19 — приложение = прямой REST.
- **Поля «Оплачено» / «Осталось оплатить»** (`ufCrm_6A72E9A2D45A4`, `ufCrm_6A72E9A2E2DA0`, `ufCrm_6ABB9B6BD012E`, `ufCrm_6ABB9B6BF189E`, `ufCrm_6ABB9B6CC3646`, `ufCrm_6A72E9B35FDA1`) унаследованы от сделок — не учитываем. Отчёт считает по `opportunity` и стадии.
- **Счета со странным сроком оплаты удалены на портале** (51 шт.: `closedate` 1970-01 — 46, 4000-01 — 4, 9000-01 — 1). Перед удалением каждый перепроверен через `crm.item.get`. Копия удалённых счетов удалена по решению пользователя. После удаления на портале 1 739 счетов.
