# Адаптация отчёта под свой портал

Стартовый документ для человека и для ИИ-агента. Цель — получить работающий отчёт на другом
портале Битрикс24 за 30–60 минут, **не переписывая приложение**.

## Как поставить задачу ИИ-агенту

Нужен ИИ-агент с доступом к терминалу (Claude Code, DeepSeek и т. п.). Работа идёт в два
сообщения — скопируйте их по очереди.

**Сообщение 1 — окружение, репозиторий, вебхук:**

```text
Подготовь рабочее место для отчёта «Дебиторка» (репозиторий maxadrom/debitorka).
1. Проверь окружение: git --version, node --version (нужен Node.js 20+), npm --version.
   Ничего не устанавливай в систему: ни Python, ни Homebrew/apt/choco, ни pip,
   ни глобальные npm-пакеты (npm install -g). Если git или Node.js 20+ нет — остановись
   и скажи мне, что поставить.
2. Склонируй https://github.com/maxadrom/debitorka.git в подпапку debitorka текущей
   рабочей папки (если она уже есть — спроси меня) и дальше работай только в ней.
3. Запусти npm test — все тесты должны пройти.
4. Прочитай целиком AGENTS.md и docs/adapt-to-portal.md.
5. Попроси у меня входящий вебхук портала (права только crm и user). Когда пришлю —
   сохрани его командой npm run dev:setup -- <URL> и больше нигде не повторяй.
6. Запусти npm run portal:probe и покажи мне результат и вопросы из раздела
   «Спросить человека». Код пока не меняй.
```

**Сообщение 2 — после ответов на вопросы `portal:probe`:**

```text
Адаптируй отчёт под мой портал строго по docs/adapt-to-portal.md, начиная с шага 4.
Приложение не переписывай и вёрстку не меняй: правится только
modules/application/portal-config.js. Мои ответы на вопросы: <ответы>.
Готово = npm test зелёный, check:live за месяц — все проверки ✅, чек-лист шага 6 пройден
в настоящем браузере, ZIP собран. В конце напомни мне удалить вебхук.
```

## Главное правило

Приложение уже работает и проверено на портале. Под новый портал меняются **только значения**
в `modules/application/portal-config.js`. Вёрстку (`index.html`, `styles.css`), загрузку
(`data-loader.js`, `api-client.js`) и формы не переписывать. Новый фильтр или колонка —
отдельная задача: план → подтверждение человека → код (см. «Рекомендации» ниже).

Чего не делать — так отчёт уже ломали:

| Нельзя | Почему |
|---|---|
| Читать репозиторий через web_fetch или пересказ субагента и писать свою версию «по мотивам» | Теряются дизайн и проверенные решения (синхронизация flatpickr через `setDate`, batch, раскладка) |
| Писать свой REST-клиент или свою сериализацию batch | `toBitrixQuery` уже проверен; самодельное кодирование «ломает» фильтры, и агент делает ложный вывод «batch не поддерживает диапазоны дат» |
| Отправлять REST-запросы через GET или form-urlencoded | Операторы фильтра (`>=`, `!=`, `@`) молча игнорируются — придут все записи. Используйте `npm run b24` |
| Проверять UI самописной заглушкой DOM | Заглушка не исполняет CSS и flatpickr: тесты зелёные, а в браузере сломано |
| Говорить «готово», не открыв приложение в браузере | Обязательная проверка — шаг 6 |
| Решать за человека, что считать «датой оплаты» или «оплаченным» | Это бизнес-решение: спросить, записать в `docs/research.md` |
| Изменять данные портала через вебхук (add, update, delete, set, batch с записью) | Отчёт только читает. Запись — только по явной просьбе человека в чате; `npm run b24` пропускает лишь методы чтения |
| Сверять цифры годом и писать свои скрипты пересчёта | Год — минута и дольше; свой скрипт ошибается сам. Сверка — `check:live` за месяц |

## Шаг 1. Окружение и репозиторий (делает агент)

Нужны только **git** и **Node.js 20+** (npm ставится вместе с Node). **Python не нужен.**

Правило «без зоопарка»: агент **ничего не ставит в систему** — ни Python, ни Homebrew/apt/choco,
ни pip, ни глобальные npm-пакеты (`npm install -g`). Всё, что нужно проекту, живёт в его папке
и удаляется вместе с ней.

```bash
git --version
node --version               # v20 или новее
git clone https://github.com/maxadrom/debitorka.git debitorka
cd debitorka
npm test                     # всё зелёное ДО первой правки
```

- Нет git или Node.js 20+ — агент останавливается, ставит человек: Node.js LTS — официальный
  установщик с nodejs.org, Git — git-scm.com (на macOS `git --version` сам предложит установить
  инструменты разработчика).
- `npm install` не нужен. Исключение — сборка ZIP там, где нет утилиты `zip` (Windows):
  тогда `npm install` **в папке проекта** (ставит `archiver` в локальный `node_modules`).

## Шаг 2. Вебхук (выпускает человек, сохраняет агент)

Агенту для разведки и проверки нужен **входящий вебхук** — ключ к REST портала.

1. На портале (нужны права администратора): **Приложения → Разработчикам → Другое → Входящий вебхук**.
2. Права (скоупы) — только эти два:
   - **`crm`** — счета, контакты, компании, стадии;
   - **`user`** — ФИО ответственных (`user.get`).

   Больше ничего не включайте: приложение только читает данные.
   Агенту через вебхук разрешено **только чтение**; менять данные портала — только по вашей явной просьбе.
3. Вебхук работает с правами создавшего его пользователя — он должен видеть все счета.
4. Скопируйте URL вида `https://<портал>.bitrix24.ru/rest/<ID>/<токен>/` и отправьте агенту в чат,
   когда он попросит. Агент сохраняет его одной командой:
   ```bash
   npm run dev:setup -- https://<портал>.bitrix24.ru/rest/<ID>/<токен>/   # → .env и dev-config.local.js
   ```
   `.env` и `dev-config.local.js` в `.gitignore`, `pack.mjs` их не упакует. Дальше скрипты
   берут вебхук из `.env` — агенту не нужно повторять его в командах и ответах.

Вебхук — это пароль ко всей CRM, а всё, что попало в чат, остаётся в логах модели. Поэтому
**после работ вебхук удаляется обязательно** (шаг 8).

## Шаг 3. Разведка портала

```bash
npm run portal:probe
```

Скрипт (только чтение) за пару секунд:

- проверит права вебхука (`crm`, `user`);
- покажет воронки и стадии счетов, отметит «Оплачен» (`SEMANTICS = S`) и «Не оплачен» (`SEMANTICS = F`);
- найдёт поля типа date/datetime с «оплат» в названии и их заполненность у оплаченных счетов;
- посчитает наши ЮЛ (`IS_MY_COMPANY = Y`);
- проверит текущие значения `portal-config.js` (✅/❌) и предложит правильные;
- выведет блок **«Спросить человека»** — эти вопросы задаются до любых правок кода.

Ручные запросы для уточнения: `npm run b24 -- <метод> '<JSON>'` (всегда POST JSON), например

```bash
npm run --silent b24 -- crm.status.list '{"filter":{"ENTITY_ID":"SMART_INVOICE_STAGE_<id воронки>"}}'
npm run --silent b24 -- crm.item.fields '{"entityTypeId":31}' | grep -i -B3 -A6 "оплат"
```

Поля «Оплачено» / «Осталось оплатить» на счетах обычно унаследованы от сделок — по ним не считаем.

## Шаг 4. Заполнить `portal-config.js`

Меняются только значения объекта `PORTAL`:

| Ключ | Что | Откуда |
|---|---|---|
| `STAGE_PAID` | стадия «Оплачен» | `portal:probe`, раздел 2, `SEMANTICS = S` |
| `STAGE_FAILED` | стадия «Не оплачен» | `portal:probe`, раздел 2, `SEMANTICS = F` |
| `PAY_DATE_FIELD` | поле «Дата оплаты» | `portal:probe`, раздел 3 (если поля нет — «Рекомендации») |
| `APP_CODE` | код приложения и имя ZIP | любой уникальный, латиница |

Повторно запустите `npm run portal:probe` — в разделе 5 всё должно быть ✅. Решения человека
запишите в `docs/research.md`.

## Шаг 5. Тесты и сверка цифр

```bash
npm test
npm run check:live -- 2026-10-01 2026-10-31      # месяц; без дат — текущий месяц
```

**Период сверки — месяц, максимум квартал.** Год не проверять: квота REST ~2 запроса/с,
год грузится минуту и дольше, а ошибок он не находит больше, чем месяц. `check:live` сам
откажется от периода длиннее 92 дней (флаг `--long` — только если человек попросил).

Ориентиры по времени на портале с ~20 000 счетов: месяц (~600 счетов) — 5–10 с,
квартал (~2 000) — 20–25 с. Загрузка: первая страница — одиночный `crm.item.list`, остальные —
`batch` пачками по 50 страниц (одна пачка = до 2 500 счетов); контакты и пользователи — тоже
`batch`. Сколько запросов ушло, `check:live` печатает сам.

`check:live` вызывает тот же `loadReport`, что и браузер, печатает «Итого» и сразу делает
**независимую сверку** по тем же сырым счетам, без лишних запросов:

- число загруженных счетов = `total` из REST, дублей нет (пагинация не потеряла страниц);
- «Должен всего», «Оплачено», «Просрочено», пересчитанные простой формулой, = «Итого» отчёта.

Все строки ✅ — сверка пройдена. **Свои скрипты пересчёта не писать**: они медленные и сами
ошибаются (потерянный фильтр по датам = сумма по всему порталу). ❌ — показать вывод человеку,
код наугад не менять.

Цифры сверки (только итоги, без ФИО) запишите в `docs/research.md`.

## Шаг 6. Проверка в браузере — обязательно

Запустите локальный сервер без кеша — `npm run serve` (Node, без зависимостей; в Claude Code —
`.claude/launch.json` → «static») — и откройте `http://localhost:8081/index.html`.
Отчёт загрузится с живыми данными через вебхук. Проверьте **в настоящем браузере**:

- [ ] «Итого» и «% сбора» совпадают с `check:live`;
- [ ] «Дата оплаты»: дату **кликом в календаре** и **вводом с клавиатуры** → «Применить» → цифры изменились, в URL появились `datePayFrom`/`datePayTo`;
- [ ] «Ответственный»: выбрать одного → «Применить» → остальные не пропали из списка;
- [ ] «Сбросить» очищает даты оплаты и выбор ответственных;
- [ ] перезагрузка страницы восстанавливает фильтры из URL;
- [ ] вкладки «по клиентам» / «по сотрудникам» — «Итого» совпадают;
- [ ] на ширине ≥ 1200 px фильтры справа столбиком, на узком экране — сверху;
- [ ] «Экспорт XLSX» скачивает файл с той же строкой «Итого».

Агенту без браузера: скажите человеку, что UI не проверен, и попросите пройти чек-лист.

## Шаг 7. Сборка и установка

```bash
npm run pack                          # dist/<APP_CODE>.zip; без npm install — через системный zip
unzip -l dist/<APP_CODE>.zip          # нет .env, dev-config*, tests/, *.md, package.json
```

ZIP на портал загружает человек — `docs/install.md`.

## Шаг 8. Удалить вебхук — обязательно

После приёмки отчёта: **Приложения → Разработчикам → вкладка «Интеграции»** → найдите
входящий вебхук → **Удалить**. Локально удалите `.env` и `dev-config.local.js`.
Установленному приложению вебхук не нужен — на портале оно работает через `BX24.*` от имени
пользователя. Для следующей доработки выпускается новый вебхук.

## Рекомендации: частые отличия порталов

Это не код по умолчанию, а проверенные рецепты. Применять только после решения человека,
решение записать в `docs/research.md`.

### Если поля «Дата оплаты» нет

`portal:probe` не нашёл заполненного date-поля оплаты. Варианты для человека:

1. **`movedTime`** — «Дата изменения стадии». Для счёта в стадии «Оплачен» это момент перевода
   в «Оплачен», то есть дата оплаты. Минус: если оплаченный счёт потом двигали по стадиям, дата сдвинется.
2. **`closedate`** — срок оплаты: всегда заполнен, но это план, а не факт.
3. Завести поле «Дата оплаты» в CRM и заполнять его — самый точный вариант на будущее.

Для `movedTime` важно: дата учитывается **только у оплаченного** счёта — у неоплаченного
`movedTime` тоже есть, но это не оплата. Правка в `data-loader.js`:

```js
// INVOICE_SELECT: вместо PAY_DATE_FIELD — 'movedTime'
function isDatePayInRange(inv, from, to) {
  const v = inv.stageId === STAGE_PAID ? inv.movedTime : null;   // '2026-10-08T13:20:21+03:00'
  if (typeof v !== 'string' || v.length < 10) return false;
  const dp = v.slice(0, 10);
  return dp >= from && dp <= to;
}
```

Тесты `tests/data-loader.test.js` (сценарии 3 и 3b) переписать под это правило, включая случай
«неоплаченный счёт с `movedTime` в диапазоне отсекается».

### Фильтр «Наше ЮЛ» (несколько юрлиц)

Если `portal:probe` нашёл больше одного ЮЛ, а человеку нужен разрез «от какого нашего ЮЛ счёт»:

- Поле счёта — **`mycompanyId`** («Реквизиты вашей компании»), справочник —
  `crm.company.list` с `filter: {IS_MY_COMPANY: 'Y'}`, `select: ['ID', 'TITLE']`.
- Фильтр — **на клиенте**, как «Ответственный»: пустой `@mycompanyId: []` на сервере возвращает
  только счета без значения, а список значений должен строиться по всем счетам периода.
- Поведение: multi-select, пусто = все; опция «Без нашего ЮЛ» для счетов с `mycompanyId = 0`;
  в подписи — число счетов периода; список ответственных строится по счетам выбранных ЮЛ.
- Состояние — в URL (`myCompanyId`, допустим `0`).
- Где править: `INVOICE_SELECT` и фильтрация в `data-loader.js` (вернуть `myCompanies` в
  контракте `loadReport`), дефолт/URL в `filters.js`, multi-select в `filters-ui.js`
  (обобщите существующий multi-select «Ответственный» в функцию, не копируйте),
  `setMyCompanies` в `app.js`. В `styles.css` при пяти блоках фильтров —
  `grid-template-columns: repeat(3, minmax(220px, 1fr))`.
- Проверка: сумма «Должен всего» по всем ЮЛ (включая «Без нашего ЮЛ») = общему «Итого».

### Несколько воронок счетов

Код считает одну стадию «Оплачен». Если воронок несколько — спросить человека, какие
считать; затем `STAGE_PAID`/`STAGE_FAILED` превращаются в списки (`@stageId` на сервере,
`Set` в `aggregator.js`). Отдельная задача с планом.
